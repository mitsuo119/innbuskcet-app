# 文化定着プラクティス

> スクラムチームが複数スプリントを通じて検証し、定常運用としてチームに組み込まれた実践集。
> 各項目は元となったレトロアクションと適用開始スプリントを記録する。

## 1. 助っ人 handoff 運用（双方向）

- **概要**: 契約上スクラムイベント（プランニング/レビュー/レトロ）に参加できない助っ人メンバー向けに、`scrum/sprintXXX/handoff_for_helpers.md` を双方向で運用する。
- **運用ルール**:
  - Day0（プランニング後）: SM・Dev が当該スプリントのゴール／PBI／タスク／前提知識・参照リンクを記載し、Day1 朝までに共有。
  - スプリント末: Dev が「助っ人への申し送り欄」にレビュー決定事項・顧客フィードバック要点・次スプリント影響を追記。
  - 助っ人側: 不明点起票枠に Day1 朝までに疑問を起票（SM が当日中に回答）。
- **由来**: Sprint001 A-2（メモ運用化）→ Sprint002 で効果確認 → Sprint003 A-8（双方向化）で完成。

## 2. 依存更新の負債バックログ化と定期解消

- **概要**: 依存パッケージの更新（マイナー/メジャー）は技術負債として PBI 化し、計画的に解消する。
- **運用ルール**:
  - 検出: `pnpm audit` および定期的な outdated 確認で更新候補を起票。
  - PBI 化: 影響度（脆弱性 High/Critical → 最優先 / マイナー → 通常 / メジャー → 互換性確認込みで通常）で見積もり。
  - メジャー更新: プランニング時または着手前日までに PO 合意を取得（事後共有は緊急時のみ）。
  - 完了条件: 既存テスト全 PASS／`pnpm build` 成功／`pnpm audit` 該当脆弱性解消。
- **由来**: Sprint001 A-1（負債バックログ化）→ Sprint002 PBI-015 で初解消実績 → Sprint003 A-7（メジャー事前合意）で運用完成。

## 3. 障害物ログ運用

- **概要**: スプリント中の障害物は `scrum/impediment_log.csv` に記録し、解決後は `impediment_log_resolved.csv` に移送する。
- **運用ルール**:
  - 起票者は Dev・SM・PO の誰でも可。デイリースクラムで言及されたものは SM が当日中に起票。
  - status は `open` / `in_progress` / `resolved` のいずれか。`resolved` 確定後にレトロでまとめて移送。
  - スプリント末に新規ゼロでも `daily_scrum.md` に「新規障害物ゼロ」を明記し、運用継続を可視化。
- **由来**: Sprint001 A-4 で運用開始 → Sprint002/003 で 3 スプリント連続定着確認。

## 4. 追加 PBI 差し込み判断基準

- **概要**: スプリント途中で当初未計画の PBI を差し込む判断は、以下 3 条件を**全て**満たす場合のみ PO 判断で可能とする。
- **3 条件**:
  1. Day3 終了時点で計画 PBI が**全て** Done。
  2. 残バッファが**2 日以上**（1 週間スプリントの場合 Day4-5 が空く状態）。
  3. スプリントゴールの**変更を伴わない**範囲であること（ゴール変更を伴う差し込みは禁止）。
- **運用ルール**: 3 条件を満たした上で「やらない」判断（次スプリント送り）も正当。差し込み採否の理由を `daily_scrum.md` に記録。
- **由来**: Sprint002 P-2（暗黙の差し込み判断）→ Sprint003 A-6 で明文化 → PBI-019 見送り判断で実運用検証完了。

## 5. 依存メジャー更新の事前 PO 合意

- **概要**: 依存パッケージのメジャーバージョン更新は、プランニング時または着手前日までに PO へ事前共有・合意を取る。
- **運用ルール**:
  - 事後共有は緊急時（脆弱性 High/Critical 即応など）のみ許容し、後日レトロで運用妥当性を検査。
  - 互換性影響範囲（API 変更・テスト更新・ビルド設定）を Dev が事前整理して PO に提示。
- **由来**: Sprint002 P-3（vite/vitest メジャー更新の事後共有）→ Sprint003 A-7 で明文化（適用機会なしだが運用準備完了）。

## 6. 計画ポイントの設定指針

- **概要**: スプリント計画ポイントは直近平均ベロシティを**上限の参考**とし、下限寄りで計画する。
- **運用ルール**:
  - レトロアクション・リファインメント・DoD 検証の余白を確保するため、平均ベロシティの 7〜11 割を目安に計画。
  - 新 DoD 適用直後・新領域着手スプリントは更に保守的に（下限寄り）設定。
  - ストレッチ枠は原則設けない。差し込みは項目 4 の 3 条件で判定。
  - **目安下限を割って計画する場合**は、判断根拠（新領域不確実性／新雛形/新 DoD 試行／リファインメント余白の重なり 等）を**プランニング記録に明示**する。Sprint004 で 6pt（A-13 下限 8pt から ▲2pt）計画が妥当に着地した実績をエビデンスとする。
- **由来**: Sprint002 P-2 → Sprint003 A-9（7pt 下限計画）で初適用 → Sprint004 A-13 評価で「下限割れ時の根拠明示」を補強し運用完成。

## 7. a11y チェックリスト運用

- **概要**: DoD §9（アクセシビリティ）の判定手順を `project/docs/a11y_checklist.md` に標準化し、各 PBI 完了時に分散判定する。
- **運用ルール**:
  - 判定タイミングは各 PBI の Done 化直前（PR レビュー前）。Day 末や Sprint 末への集中チェックは禁止。
  - チェック項目は §9-1（キーボードのみで主要操作完結）/ §9-2（focus 可視）/ §9-3（role / aria 属性）の3軸＋コントラスト比測定手順。
  - チェックリスト改訂はレトロまたはリファインメントで合意。
- **由来**: Sprint003 P-3（a11y 手動チェックの Day4 集中／個人スキル依存）→ Sprint004 A-10 で雛形化＋分散判定を実運用 → 効果実証で卒業。
