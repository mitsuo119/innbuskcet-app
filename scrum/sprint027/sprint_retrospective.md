## Keep / Problem / Try（5 観点）

### Keep（維持）— 6 件

- **個人（伊藤）**: PBI-102（1pt）を DAY1 で完遂。`parsePathname()` の **1 行追加**で全ルートの末尾スラッシュ問題を根治し、`/` の退行ゼロを目視＋ 11 URL 機械 HTTP 検証で確認。最小差分で副作用を抑える判断が秀逸。
- **個人（田中）**: PBI-103（1pt）を DAY1 で完遂し回帰テストを `Router.trailingSlash.test.tsx` **25 ケース**まで拡張（代表 8 URL × 有無 + `/` 正規化対象外 + `not-found` 末尾スラッシュ後 404 維持）。**1 行修正に対する防壁を最初から十分厚く張った**点が再発防止上きわめて重要。
- **個人（田中・山本・中村）**: PBI-104（2pt）を **Playwright 新規 devDep 追加 → preview 43/0 PASS → DAY4 の h1 抽出範囲改善（`[data-prerender]` 配下に限定 → `<noscript>` 誤検知解消）まで 3 日で完遂**。DAY4 改善は「動いた後でも自分たちで再点検して品質を上げる」姿勢の好例。
- **個人（高橋）**: PBI-105（1pt）を **Day0 一発**で DoD §4-3 追記＋ history 追記＋渡辺書面合意まで完遂し、Sprint027 内の他 PBI を全て新 DoD（22 項目）で判定可能にした。**プロセス整備を先に通すことで実装 PBI のゴール条件を構造的に強化**できた。
- **プロセス**: **オーケストレータ（SM 高橋）の事前実機調査が致命バグ発見の起点**。Sprint026 で「コンテンツ修正完了」と報告した直後に本番実機で代表ルートを開く確認を行ったことで、JS 実行後の 404 化を Sprint027 着手前に発見でき、最短経路で根治 PBI を組成できた。
- **ツール / 完成の定義**: 新設 DoD §4-3 と `check:outcome` の組合せが **PBI-102/103/104/105 すべてで 22/22「はい」**として実用に乗った。`pnpm run check:outcome -- --target=preview|prod` の **1 コマンド運用**は佐藤からも「運用上ありがたい」と直接評価。

### Problem（課題）— 5 件

- **完成の定義（最重要）**: Sprint026 までの DoD §4 は「dist の view-source: 視点」までしか見ておらず、**「JS 実行後・本番ホスティング上での実アウトカム」**が抜けていた。1 行で直る欠陥が **本番公開〜実機レビューまで生き残った**事実は、A-120/A-121 を入れた今でも「DoD 完了 ≠ ユーザーに価値が届いている」のギャップが残っていることを示す（特に本番反映前の preview PASS は **prod の代理であって prod ではない**）。
- **プロセス（最重要 / 価値遅延構造）**: **本番デプロイがスクラムの完成フロー外**に置かれている。Sprint027 で技術的にバグは根治し DoD も拡張したが、**本番に反映するまではエンドユーザー／クローラー視点では何も改善されていない**。今 SP の prod `check:outcome` が FAIL=42 のまま終わったのはこの構造の象徴で、AdSense 再申請（PBI-094）は本来 Sprint027 で着手判断できたはずが Sprint028 へずれ込んだ。
- **プロセス**: AdSense 再申請という**「失敗できない一発勝負」**の前提条件チェックリスト（`adsense_resubmission_checklist.md`）が Sprint026 時点で整備されていたにもかかわらず、**「JS 実行後にトップ以外も 404 化しないこと」項目が無かった**（DAY3 で §4-7 を追記して解消）。これも「DoD §4-3 が無かったから checklist にも入っていなかった」という同根の問題。
- **個人（伊藤・田中）**: ルータの末尾スラッシュ正規化は **既存ルーティング設計時にカバーすべき仕様**であり、Sprint020（History API 移行）時点で検討余地があった。本番ホスティング側のリダイレクト挙動（`/about` → `/about/`）が組合さって初めて顕在化したが、**「ホスティング層と SPA ルータの I/F 仕様」を機械的に検証する観点**が当時無かった。
- **ツール**: `check:outcome` は新設できたが **preview と prod の両方を CI / DAY5 品質ゲートで自動走行する仕組みは未整備**。今は手動で `--target=preview|prod` を切り替える運用で、本番反映後の prod 再計測が「人が思い出して走らせる」状態。再発防止強度はまだ A-120/A-121 だけでは不十分。

### Try（試行）— 5 件

- **本番デプロイの PBI 化定常運用 + デプロイ手順／ロールバック手順の文書化（最優先 / Problem 2 起因）**: Sprint028 で **PBI-106（本番デプロイ実施 + prod `check:outcome` PASS）** を投入することは Sprint Review で確定済（A-123 として明示管理化）。これに合わせ **「本番デプロイは PBI として常に可視化する」ことを文化として暫定運用** し、2 連続 SP で運用できれば `scrum_team_culture.md` に反映する。
- **CD（本番デプロイ自動化）整備の検討（最優先 / Problem 2 起因）**: PBI-106 完遂後、**GitHub Pages / カスタムドメイン環境への自動デプロイ + デプロイ後の `check:outcome --target=prod` を CI で自動走行**する CD パイプライン整備を ADR 検討対象として起票（A-124）。比較軸は（a）GitHub Actions ベースで完結するか（b）デプロイ後 prod 検証ゲートの組込み可否（c）ロールバック容易性（d）秘密情報運用（OIDC 継続）。Sprint028 リファインメントで PBI 化要否を判定。
- **`check:outcome` の CI / DAY5 品質ゲート組込み（Problem 5 起因）**: 現状の手動運用から `pnpm test` 系または GitHub Actions ワークフローへ組み込み、**少なくとも preview モードは PR ごとに自動走行**させる（A-125）。prod モードは本番デプロイ後の post-deploy hook で自動走行（A-124 の一部として実装）。
- **DoD 完了の定義に「本番反映を経た価値到達」までを含めるかの議論（Problem 1 起因）**: 現行 DoD は「インクリメント＝ deployable」だが本番デプロイ責務は外。**スクラムガイド準拠の範囲で「DoD §4-4：該当機能が本番反映後に prod `check:outcome` で PASS していること」相当の追加要否**を Sprint028 レトロまでに継続議論（A-126）。即時 DoD 化はチームの自律性を損なう可能性があるため、**まずは PBI-106 のような本番反映 PBI で個別に担保**し、2〜3 スプリント運用後に DoD 化要否を再判定する漸進方針。
- **オーケストレータ事前実機調査の運用化（Keep 5 起因の前向き Try）**: 今回 SM の事前実機調査が致命バグ発見の起点になった事実を踏まえ、**Sprint Review 直前と次 SP プランニング直前の 2 タイミング**で「本番／preview の代表ルートを実機で開く 5 分チェック」を SM タスクとして暫定運用（A-127）。2 連続 SP で機能すれば `scrum_team_culture.md` に反映。
