## 【追記 2026-06-02】Sprint005 レビュー後の追加要望（Sprint006 以降向け）

Sprint005 で PBI-023（3 ブロック記述 UI）/ PBI-024（模範比較）が投入され、実際に使い始めた結果、
**学習価値は大きく上がった一方で、運用面で 3 つの強い不満点**が出てきた。
Sprint006 のリファインメント／プランニングでこれらを最優先級で取り上げてほしい。

### 要望 A: 「答え」が A/B/C 記号だけだと意味が瞬時に判らない（重要度: High）

- 現在は選択肢が **A / B / C** の 3 択。本文中で「正解は A」と表示されても、
  自分の癖で「パターン 7」「優先度 1」などの**数値感覚**で考えてしまい、A/B/C の意味が一拍遅れる。
- 結果画面・履歴・解説のいずれにおいても、回答の意味（最優先 / 中優先 / 低優先 と、その短い定義）が
  **記号と一緒に常時見える**ようにしてほしい。
- できれば「最優先（A）= 即時着手すべき」「中優先（B）= 本日中に着手」「低優先（C）= 委任 or 後回し」のような
  **短い意味ラベル**を、案件画面・解説・履歴の全箇所で統一表示したい。
- 受入イメージ:
  - 案件画面の A/B/C ボタンに加え、結果表示・履歴行・模範比較ヘッダーでも「A（最優先）」のように
    **記号 ＋ 日本語ラベル ＋ 1 行の意味**がワンセットで表示される。
  - スクリーンリーダーでも「エー、最優先、即時着手」のように読み上げられる（DoD §9 整合）。

> 補足: PBI-019 のテーマ系で A/B/C ボタンに「◎/○/△＋名称」を出している実装があるので、
> その**ラベル定義を結果・履歴・模範比較ビューにも横展開**するイメージ。

### 要望 B: 判断・理由・アクションの記述が「毎問やるには重い」（重要度: High）

- PBI-023 で 3 ブロック記述ができるようになったのは大きな前進。
- ただし**毎問フルで書くのは負担が大きく**、隙間時間（電車内 5 分など）の演習には向かない。
- 「書かなくても演習が進められる」「書くなら書く、書かないなら書かない」を**ユーザが選べる**ようにしたい。
- 補助案（どれか／組合せで実現したい）:
  - **任意入力化**: 3 ブロックは空欄のまま A/B/C 回答に進める（現在の挙動の確認＋明示化）
  - **記述スキップ動線**: 「今回は書かない」ボタンで textarea を非表示／折りたたみ
  - **テンプレ補助**: 「フォロー」「委任」「期限明示」など**チェック式の選択肢**を用意し、
    タップだけで簡易回答が組み立てられる（自由記述は任意で残す）

### 要望 C: 「Quick モード / Deep モード」の切替が欲しい（重要度: High。要望 B と一体）

- 隙間時間と腰を据えた学習を**1 つのアプリで両立**したい。以下 2 モードの切替 UI を最上位に置きたい。

| モード       | 動線                                                                         | 想定シーン                          |
| ------------ | ---------------------------------------------------------------------------- | ----------------------------------- |
| **Quick**    | 案件本文 → A/B/C 回答 → 解説 →「次へ」（記述欄は非表示）                     | 通勤・隙間 5 分。優先度判断だけ反復 |
| **Deep**     | 回答前 3 ブロック記述 → A/B/C → 模範比較 → 解説（現 Sprint005 の標準フロー） | 自宅・週末。型を体に入れる練習      |
| （将来候補） | **Exam**: PBI-027 の 20 問 90 分連続演習                                     | 試験 2 週間前の本番リハ             |

- モード設定は **localStorage に保存**して次回起動時にも維持してほしい（モード設定は永続化 OK。記述本文は引き続きセッション内のみ）。
- モード切替時に**履歴が混ざらない**ように、モードごとに正答率を集計するか、履歴行にモードを表示してほしい
  （Sprint004 の PBI-022「モード別正答率」の枠を再利用できるとよい）。

### この 3 要望の優先順位（佐藤の希望）

1. **要望 A（A/B/C ＋意味ラベル全箇所表示）**: 軽量・全画面に効く・即効性あり。**Sprint006 で必ず**取りたい。

### 要望 D の概要

- PBI-023（3 ブロック記述）で書いた「判断 / 理由 / アクション」を、**AI が読んで評価フィードバックを返す**機能。
- 自己採点（チェックリスト形式）は**廃止 or オプション扱い**に格下げし、AI 評価を主軸にしたい。
- 学習者の心理的ハードル（自分で○×を付けるのは気が乗らない／甘くなる）を下げ、**「書いて → AI に見てもらう」という能動学習サイクル**を作る。

### 検討すべき論点（PO 鈴木・SM 高橋・開発者へインプット）

#### 論点 1: AI フィードバックの**形式**

下記のうち、どれを採用するか（複数組合せ可）。佐藤の希望は **(b) + (c)**。

| 案  | 形式                                                         | メリット               | デメリット                     |
| --- | ------------------------------------------------------------ | ---------------------- | ------------------------------ |
| (a) | 合格 / 不合格の二択判定                                      | シンプル               | フィードバック性に乏しい       |
| (b) | ◎ / ○ / △ の 3 段階評価（ブロック別 or 総合）                | 視覚的に分かりやすい   | 評価軸の根拠説明が別途必要     |
| (c) | 自然言語コメント（例: 「理由の 5W1H が不足。Why が弱い」）   | 学習価値が最も高い     | 評価のブレ・文体の安定性が課題 |
| (d) | 改善提案（例: 「『なぜなら〜』の形で理由を補強してみては」） | 行動につながる         | 模範解答との重複の整理が必要   |
| (e) | 採点ポイント（5W1H/委任/フォロー/関連）への該当チェック      | PBI-024 の評価軸と整合 | ルールベースで十分な可能性あり |

#### 論点 2: AI 評価の**タイミング**

- (i) 記述後「AI に見てもらう」ボタンを明示的に押す（佐藤推奨。コストとレート制限に配慮しやすい）
- (ii) A/B/C 回答確定と同時に自動評価
- (iii) 模範回答表示と同時に自動評価

#### 論点 3: **どの AI を使うか**（最大の論点）

現アプリは **ローカルブラウザ単独・サーバーレス・認証/API 不使用** が大原則（order005 非機能・制約）。
AI 評価を入れるなら、この前提を一部見直す必要がある。

| 方式                                        | 概要                                                                                                  | 利点                             | 課題                                                           |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------- |
| (α) **外部 API 直接呼出**（OpenAI/Claude）  | ブラウザから API キーを使って呼出                                                                     | 評価品質が高い                   | API キーがブラウザに露出 → セキュリティ NG。コスト負担者が不明 |
| (β) **BYOK（ユーザが自分の API キー入力）** | 設定画面で API キーを入力させ、localStorage 保存                                                      | コスト負担者が明確（ユーザ自身） | 一般ユーザにはハードル高。DoD §10-3 で慎重な扱いが必要         |
| (γ) **薄い中継 API（最小サーバ）**          | Vercel Functions 等で API キーを秘匿し、レート制限                                                    | セキュリティ確保しやすい         | サーバーレスではあるが**設計大変更**。運用コスト発生           |
| (δ) **ブラウザ内ローカル LLM**（WebLLM 等） | 量子化モデルをブラウザで実行                                                                          | プライバシー・コスト 0           | 初回 DL が大きい（数百 MB〜）。日本語評価品質が未知            |
