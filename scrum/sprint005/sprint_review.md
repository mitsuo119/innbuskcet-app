## 1. インクリメントのデモ（伊藤）

### 1-1. 学習フロー全体

1. ランダム出題 → 案件本文表示
2. **回答前から** 判断 / 理由 / アクション の 3 つの textarea が編集可能（先に考えを言語化してから A/B/C を選ぶ動線）
3. A/B/C 回答 → 記述欄が `disabled` でロック（後から書き換え不可）
4. 自分の記述プレビュー（`WritingPreview`）と **模範解答骨格（`ModelAnswerView`）** が並んで表示
5. 解説（`ExplanationView`）→「もう一度」または「次の問題」

### 1-2. PBI-023: 判断・理由・アクション 3 ブロック記述 UI

- `domain/writing.ts`：`WritingEntry` 型と `validateWritingBlock` / `createEmptyWritingEntry` / `isWritingEntryEmpty` を純粋関数で実装。最大長 500 を境界値テスト（499 / 500 / 501 / 空文字 / 型破壊）で保証（DoD §10-1）。
- `ui/WritingInput.tsx`：textarea×3、`<label htmlFor>` ＋ `aria-label`、`role="group"`、文字数カウンタ `aria-live="polite"`、回答後 `disabled`、最大文字数到達の補助テキスト。
- `ui/WritingPreview.tsx`：`<dl>/<dt>/<dd>` で意味づけ。`pre-wrap` で改行保持、全空時は「未記述」案内。**`dangerouslySetInnerHTML` 不使用**（DoD §10-2）。
- `domain/shortcut.ts`：`isEditableTarget()` を新設し textarea/input/select/contenteditable 中の A/B/C/Enter 誤発火を防止。`shortcut.test.ts` で 6 件追加検証。
- `App.tsx`：CaseView 直後に WritingInput を配置（回答前入力可）。`handleNext` / `handleModeChange` で `createEmptyWritingEntry()` 初期化、`handleRetry` は writingEntry 保持で再回答可。

### 1-3. PBI-024: 模範回答骨格との比較表示

- `data/cases.json`：先行 10 件（case-001〜010、A:4 / B:2 / C:4 = A/B/C 各 30%）に `modelAnswer{judgment,reason,action}` を投入。残 30 件は段階移行扱いでオプショナル。
- `domain/case.ts`：`ModelAnswer` 型追加、`Case.modelAnswer?` をオプショナル化。
- `domain/loader.ts`：`parseModelAnswer()` で必須キー存在 / 文字列型 / 非空文字列を検証。**不整合時は throw せず undefined フォールバック**（`console.warn` で開発者通知）。Case ロードは継続（DoD §10-3）。
- `ui/ModelAnswerView.tsx`：`<dl>/<dt>/<dd>` で 3 ブロック表示。`modelAnswer` undefined または `visible=false` のとき「**模範解答準備中**（この案件はまだ模範回答骨格が整備されていません）」プレースホルダ。**XSS 文字列のエスケープを vitest で証明**（`<script>` / `<img onerror>` / `<b>` を素のテキストとして描画）。
- `App.tsx`：回答後に WritingPreview の直後・ExplanationView の手前に ModelAnswerView を配置。`visible={!!judgement}` で再回答前は自然に非表示。

### 1-4. 範囲外（明示）

- 採点ポイントチェックボックス（自己採点用）と左右並列レイアウトはバックログ TASK 説明にあったが、PBI-024 受入基準に直接含まれないため Sprint006 以降の拡張余地として残置（PBI-029 で吸収予定）。

## 4. ステークホルダーフィードバック

### 4-1. 佐藤（顧客 / 学習者）— 「昇進試験合格直結か」の視点

#### 高評価（合格に効く）

1. **「ついに本番に近づいた」**：A/B/C を選ぶ前に判断・理由・アクションを言語化させる動線は、本番試験での記述準備として理想的。「優先度クイズ」の枠を脱した。
2. **回答前入力 → 回答後ロック**：考えを書いてから優先度を選ぶ流れにすることで、「直感で A/B/C を当てに行く」浅い学習を防いでいる。
3. **模範解答骨格との並列表示**：自分の記述と模範を同一画面で見比べられるのは chapter09 の合格答案の型を体に入れる上で実用的。「準備中」プレースホルダも誠実で、整備中であることが透明に伝わる。
4. **shortcut の textarea ガード**：記述中に A/B/C キーで誤確定しないのは細部だが必須の配慮。安心して書ける。
5. **DoD §10 を初適用しても着地**：セキュリティ品質を強化しながら計画 6pt を完走したことは、品質と速度の両立として評価。

#### 改善提案（次スプリント以降）

1. **採点ポイントの自己チェック導線が欲しい（最重要）**：模範を眺めるだけでは「自分の記述のどこが弱いか」が言語化されない。判断が明確か / 5W1H があるか / 委任観点 / フォロー観点 のチェックリストで自己採点したい。→ **PBI-029** に既存。Sprint006 で Ready 化を期待。
2. **時間制限モード（20問90分）は次スプリント最優先で**：記述ができるようになった今、本番タイムマネジメントの欠落が最大のギャップ。**PBI-027 を Sprint006 最優先**（プランニングで合意済）。
3. **模範解答が 10/40 件なのは少ない**：案件の 4 分の 1 しか比較学習できない。PBI-024 の枠で順次拡充するか、独立 PBI で計画的に整備したい。
4. **`scoringPoints` を投入したのに使っていない**：データだけ用意して UI が無いのはもったいない。PBI-029 で必ず活用すること。
5. **記述内容のセッション内保持は OK だが、リロードで消える注意書きが欲しい**：誤ってリロードして書いた内容を失う恐れがある。注意書きで十分。
