## 【追記 2026-06-02】Sprint005 レビュー後の追加要望（Sprint006 以降向け）

Sprint005 で PBI-023（3 ブロック記述 UI）/ PBI-024（模範比較）が投入され、実際に使い始めた結果、
**学習価値は大きく上がった一方で、運用面で 3 つの強い不満点**が出てきた。
Sprint006 のリファインメント／プランニングでこれらを最優先級で取り上げてほしい。

### 要望 A: 「答え」が A/B/C 記号だけだと意味が瞬時に判らない（重要度: High）

- 現在は選択肢が **A / B / C** の 3 択。本文中で「正解は A」と表示されても、
  自分の癖で「パターン 7」「優先度 1」などの**数値感覚**で考えてしまい、A/B/C の意味が一拍遅れる。
- 結果画面・履歴・解説のいずれにおいても、回答の意味（最優先 / 中優先 / 低優先 と、その短い定義）が
  **記号と一緒に常時見える**ようにしてほしい。
- できれば「最優先（A）= 即時着手すべき」「中優先（B）= 本日中に着手」「低優先（C）= 委任 or 後回し」のような
  **短い意味ラベル**を、案件画面・解説・履歴の全箇所で統一表示したい。
- 受入イメージ:
  - 案件画面の A/B/C ボタンに加え、結果表示・履歴行・模範比較ヘッダーでも「A（最優先）」のように
    **記号 ＋ 日本語ラベル ＋ 1 行の意味**がワンセットで表示される。
  - スクリーンリーダーでも「エー、最優先、即時着手」のように読み上げられる（DoD §9 整合）。

> 補足: PBI-019 のテーマ系で A/B/C ボタンに「◎/○/△＋名称」を出している実装があるので、
> その**ラベル定義を結果・履歴・模範比較ビューにも横展開**するイメージ。

### 要望 B: 判断・理由・アクションの記述が「毎問やるには重い」（重要度: High）

- PBI-023 で 3 ブロック記述ができるようになったのは大きな前進。
- ただし**毎問フルで書くのは負担が大きく**、隙間時間（電車内 5 分など）の演習には向かない。
- 「書かなくても演習が進められる」「書くなら書く、書かないなら書かない」を**ユーザが選べる**ようにしたい。
- 補助案（どれか／組合せで実現したい）:
  - **任意入力化**: 3 ブロックは空欄のまま A/B/C 回答に進める（現在の挙動の確認＋明示化）
  - **記述スキップ動線**: 「今回は書かない」ボタンで textarea を非表示／折りたたみ
  - **テンプレ補助**: 「フォロー」「委任」「期限明示」など**チェック式の選択肢**を用意し、
    タップだけで簡易回答が組み立てられる（自由記述は任意で残す）

### 要望 C: 「Quick モード / Deep モード」の切替が欲しい（重要度: High。要望 B と一体）

- 隙間時間と腰を据えた学習を**1 つのアプリで両立**したい。以下 2 モードの切替 UI を最上位に置きたい。

| モード       | 動線                                                                         | 想定シーン                          |
| ------------ | ---------------------------------------------------------------------------- | ----------------------------------- |
| **Quick**    | 案件本文 → A/B/C 回答 → 解説 →「次へ」（記述欄は非表示）                     | 通勤・隙間 5 分。優先度判断だけ反復 |
| **Deep**     | 回答前 3 ブロック記述 → A/B/C → 模範比較 → 解説（現 Sprint005 の標準フロー） | 自宅・週末。型を体に入れる練習      |
| （将来候補） | **Exam**: PBI-027 の 20 問 90 分連続演習                                     | 試験 2 週間前の本番リハ             |

- モード設定は **localStorage に保存**して次回起動時にも維持してほしい（モード設定は永続化 OK。記述本文は引き続きセッション内のみ）。
- モード切替時に**履歴が混ざらない**ように、モードごとに正答率を集計するか、履歴行にモードを表示してほしい
  （Sprint004 の PBI-022「モード別正答率」の枠を再利用できるとよい）。

### この 3 要望の優先順位（佐藤の希望）

1. **要望 A（A/B/C ＋意味ラベル全箇所表示）**: 軽量・全画面に効く・即効性あり。**Sprint006 で必ず**取りたい。

## 【追記 2026-05-02】記述評価を「自己採点」から「AI 評価フィードバック」に転換したい（要望 D）

Sprint006 で Ready 化した **PBI-029（記述モードの自己採点チェックリスト）** について、ユーザ（上長）から
**「記述を自己採点ではなく、AI が評価フィードバックできるようにしたほうが良いのではないか」**
という強い問題提起があった。佐藤としても、自己採点では「自分に甘い／辛い」のブレが出やすく、
**昇進試験合格直結という order005 の本筋から見て、AI による客観評価のほうが学習価値が高い**と判断する。

Sprint006 プランニング前のリファインメントで、PBI-029 の方向性そのものを再検討してほしい。

### 要望 D の概要

- PBI-023（3 ブロック記述）で書いた「判断 / 理由 / アクション」を、**AI が読んで評価フィードバックを返す**機能。
- 自己採点（チェックリスト形式）は**廃止 or オプション扱い**に格下げし、AI 評価を主軸にしたい。
- 学習者の心理的ハードル（自分で○×を付けるのは気が乗らない／甘くなる）を下げ、**「書いて → AI に見てもらう」という能動学習サイクル**を作る。

### 検討すべき論点（PO 鈴木・SM 高橋・開発者へインプット）

#### 論点 1: AI フィードバックの**形式**

下記のうち、どれを採用するか（複数組合せ可）。佐藤の希望は **(b) + (c)**。

| 案  | 形式                                                             | メリット                       | デメリット                       |
| --- | ---------------------------------------------------------------- | ------------------------------ | -------------------------------- |
| (a) | 合格 / 不合格の二択判定                                          | シンプル                       | フィードバック性に乏しい         |
| (b) | ◎ / ○ / △ の 3 段階評価（ブロック別 or 総合）                    | 視覚的に分かりやすい           | 評価軸の根拠説明が別途必要       |
| (c) | 自然言語コメント（例: 「理由の 5W1H が不足。Why が弱い」）       | 学習価値が最も高い             | 評価のブレ・文体の安定性が課題   |
| (d) | 改善提案（例: 「『なぜなら〜』の形で理由を補強してみては」）     | 行動につながる                 | 模範解答との重複の整理が必要     |
| (e) | 採点ポイント（5W1H/委任/フォロー/関連）への該当チェック          | PBI-024 の評価軸と整合         | ルールベースで十分な可能性あり   |

#### 論点 2: AI 評価の**タイミング**

- (i) 記述後「AI に見てもらう」ボタンを明示的に押す（佐藤推奨。コストとレート制限に配慮しやすい）
- (ii) A/B/C 回答確定と同時に自動評価
- (iii) 模範回答表示と同時に自動評価

#### 論点 3: **どの AI を使うか**（最大の論点）

現アプリは **ローカルブラウザ単独・サーバーレス・認証/API 不使用** が大原則（order005 非機能・制約）。
AI 評価を入れるなら、この前提を一部見直す必要がある。

| 方式                                       | 概要                                                               | 利点                             | 課題                                                           |
| ------------------------------------------ | ------------------------------------------------------------------ | -------------------------------- | -------------------------------------------------------------- |
| (α) **外部 API 直接呼出**（OpenAI/Claude） | ブラウザから API キーを使って呼出                                  | 評価品質が高い                   | API キーがブラウザに露出 → セキュリティ NG。コスト負担者が不明 |
| (β) **BYOK（ユーザが自分の API キー入力）** | 設定画面で API キーを入力させ、localStorage 保存                   | コスト負担者が明確（ユーザ自身） | 一般ユーザにはハードル高。DoD §10-3 で慎重な扱いが必要         |
| (γ) **薄い中継 API（最小サーバ）**         | Vercel Functions 等で API キーを秘匿し、レート制限                 | セキュリティ確保しやすい         | サーバーレスではあるが**設計大変更**。運用コスト発生           |
| (δ) **ブラウザ内ローカル LLM**（WebLLM 等） | 量子化モデルをブラウザで実行                                       | プライバシー・コスト 0           | 初回 DL が大きい（数百 MB〜）。日本語評価品質が未知             |
| (ε) **ルールベース疑似 AI フィードバック** | 模範解答骨格との一致語彙・キーワード（5W1H/委任/フォロー）を判定し、テンプレ文で「AI 風」コメント生成 | 外部依存ゼロ・即実装可・無料     | 「本物の AI」ではない。ただし**学習効果は十分**ある可能性大     |

#### 論点 4: PBI-029 との関係（Sprint006 での扱い）

PBI-029 は Sprint006 リファインメントで Ready 化されたばかり（既存記述 + scoringPoints 活用）。以下 3 案：

- **案 X**: PBI-029 を**そのまま実施**し、AI 評価は新規 PBI として Sprint007 以降に切り出す（保守的）
- **案 Y**: PBI-029 を**「ルールベース疑似 AI フィードバック」に方向転換**して Sprint006 で実施（佐藤推奨）
  - 既存の scoringPoints / modelAnswerSkeleton と一致語彙を判定 → 「5W1H チェック」「委任の言及」「フォロー期限の明示」「関連案件への言及」を ◎ / ○ / △ で出し、定型コメントを返す
  - 完全な「AI」ではないが、**ユーザ体験としては「AI が見てくれた」感**を出せる
  - Sprint007 以降で本物の LLM 連携（β or δ）に差し替える二段構え
- **案 Z**: PBI-029 を**Drop**し、最初から本物の AI 連携 PBI として Sprint007 以降に新規起票（大改革）

### 佐藤の推奨方針

- **論点 1**: (b) 3 段階評価 ＋ (c) 短い自然言語コメント。`例: 「○ 理由は概ね妥当。ただし 5W1H の Why が弱い」`
- **論点 2**: (i) ボタン押下式。コスト管理しやすく、誤発火も防げる
- **論点 3**: **段階アプローチ**を提案
  - **第 1 段階（Sprint006）**: (ε) ルールベース疑似 AI で実装。既存資産（scoringPoints / modelAnswerSkeleton）の活用で高い学習価値を低リスクで提供
  - **第 2 段階（Sprint007 以降）**: (β) BYOK 方式 or (δ) WebLLM をオプション機能として追加検討。コアアプリは引き続きサーバーレスを維持
- **論点 4**: **案 Y を推奨**。PBI-029 を「ルールベース疑似 AI フィードバック」に方向転換（仮 PBI-029'）。完全な LLM 連携は別 PBI（仮 PBI-038: AI 評価本格対応）として Sprint007 以降の候補に積む

### 1. 要望 D 第 1 段階：ルールベース評価ロジックの具体仕様

#### 1-1. 評価軸（3 ブロック × 共通採点ポイント）

| 評価軸                  | 入力                                                       | 判定方法                                                                                                                                                          | 出力                                                                |
| ----------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **(1) 判断の一致度**    | A/B/C 選択値 ＋ 模範解答の `correctPriority`               | 完全一致 = ◎ ／ 1 段階ずれ（A↔B または B↔C）= ○ ／ 2 段階ずれ（A↔C）= △                                                                                          | 判断ブロック総合評価 ◎/○/△＋定型コメント                            |
| **(2) 理由のキーワード**| 理由テキスト ＋ `modelAnswer.reason` の主要語彙            | 模範 reason から名詞・動詞を抽出（簡易な正規表現／既知語リスト）し、ユーザ記述に含まれる語の数を集計。3 個以上 = ◎ ／ 1〜2 個 = ○ ／ 0 個 = △                       | 理由ブロック総合評価＋「○○の観点が含まれています」コメント         |
| **(3) アクションの具体性**| アクションテキスト                                       | 文字数 ＋ 動詞数（〜する／〜依頼／〜共有／〜確認 等）でスコアリング。80 字以上 ＋ 動詞 3 個以上 = ◎ ／ 40 字以上 = ○ ／ それ未満 = △                                | アクションブロック総合評価＋長さ／具体性の定型コメント              |
| **(4) 採点ポイント該当**| 3 ブロック合算テキスト ＋ `scoringPoints[]` 各項目         | `scoringPoints[]` の各項目について、項目名・関連キーワード（後述キーワード辞書）に該当する語が記述に含まれるかを判定。該当 = ✓ ／ 非該当 = ✗                       | 採点ポイント別チェック一覧（5〜7 項目、`scoringPoints` の順序維持） |

> いずれも **完全一致語彙ではなく部分一致（`String.prototype.includes`）** で十分。形態素解析は導入しない（依存追加は避ける）。

#### 1-2. キーワード辞書（共通採点軸 × 5W1H/委任/フォロー/関連）

`scoringPoints[]` が未整備の案件向けフォールバックとしても流用する。`domain/feedbackKeywords.ts` を新設し、唯一の定義源とする想定：

- `scoringPoints[]` の項目文字列に対し、上記カテゴリ名（"who" / "delegate" 等）または日本語キーワード群のいずれかが含まれる項目について判定する。
- 例：`scoringPoints[i] = "委任先を明確にしているか"` → `delegate` カテゴリのキーワード辞書を参照 → ユーザ記述に「依頼」「任せる」等があれば ✓。

#### 1-3. `scoringPoints[]` フィールドの活用方法（PBI-029 受入基準への組み込み）

- 現 PBI-029 の自己採点チェックリスト UI を **「AI 評価結果の表示パネル」に転換**。
- `scoringPoints[]` がある案件: その配列順に評価結果（✓/✗ ＋ 短コメント）を表示。
- `scoringPoints[]` が無い案件: 1-2 のキーワード辞書ベースで汎用 5 項目（5W1H / 委任 / フォロー / 関連 / 具体性）の評価結果を表示。
- どちらの場合も最終的に **「総合 ◎ / ○ / △ ＋ ブロック別 ◎ / ○ / △ ＋ 採点ポイント該当一覧」** の 3 段表示で UI を統一。

### 2. PBI-029 の再定義（PO 鈴木への要望）

現バックログの PBI-029（自己採点チェックリスト）を、以下のように **タイトル・受入基準ともに上書きで再定義**してほしい。

#### 提案：PBI-029（再定義）「ルールベース AI 評価フィードバック表示」

- **ストーリー**: 学習者として、3 ブロック記述に対してルールベースの AI 風フィードバック（◎/○/△＋短コメント＋採点ポイント該当）を即座に得たい。自己採点の主観ブレを排し、客観的な気付きを反復するため。
- **受入基準（案）**:
  1. 3 ブロック記述後、「AI に見てもらう」ボタンを押すとブロック別 ◎/○/△ 評価と短コメント（FEEDBACK_TEMPLATES）が表示される
  2. 判断の評価は A/B/C 選択値と `correctPriority` の段階差で決定（一致=◎ / 1段差=○ / 2段差=△）
  3. 理由・アクションの評価は 1-1 表のロジック（キーワード一致数 / 文字数＋動詞数）で決定
  4. `scoringPoints[]` がある案件は配列順に該当チェック（✓/✗）が表示される
  5. `scoringPoints[]` が無い案件は汎用 5 項目（5W1H/委任/フォロー/関連/具体性）にフォールバック
  6. 評価結果はセッション内のみ保持・リロードで初期化（記述本文と同一方針）
  7. 評価ロジックは純粋関数として `domain/feedback.ts` に切出し、単体テスト 10 件以上で挙動を保証
  8. キーワード辞書（`FEEDBACK_KEYWORDS`）・テンプレ（`FEEDBACK_TEMPLATES`）は単一定義源として `domain/` に集約
  9. キーボードのみで全操作可能（DoD §9-1）／ SR で評価結果を読み上げ可能（DoD §9-3）
  10. `dangerouslySetInnerHTML` 不使用（DoD §10-2）／ ユーザ記述は React テキスト描画
  11. DoD 全項目（21 項目）を満たす
- **サイズ**: 現 2pt → **3pt に再見積**（評価ロジック純粋関数＋テスト＋ UI 改修＋既存 PBI-024 採点チェックボックスとの統合整理が必要なため）
- **優先度**: High 維持
- **状態**: Ready（現状維持。リファインメント時に受入基準を上書き）
- **タイトル変更案**: `記述モードの自己採点チェックリスト(...)` → `ルールベースAI評価フィードバック表示(PBI-024 scoringPoints[]活用 / 判断一致度・キーワード・具体性で◎○△評価)`

#### 補足：自己採点チェックリストの扱い

- PBI-024 で既に投入済の「採点ポイントのチェックボックス（自己チェック）」UI は **そのまま残す**。AI 評価と自己採点が**併存**することで、ユーザは「自分でチェック → AI に見てもらう」の 2 段階確認が可能。
- 「自己採点だけを廃止」する必要は無い。AI 評価が**主軸**になることが重要。
