# 文化定着プラクティス

> スクラムチームが複数スプリントを通じて検証し、定常運用としてチームに組み込まれた実践集。
> 各項目は元となったレトロアクションと適用開始スプリントを記録する。

## 1. 助っ人 handoff 運用（双方向 / 構造化還流欄）

- **概要**: 契約上スクラムイベント（プランニング/レビュー/レトロ）に参加できない助っ人メンバー向けに、`scrum/sprintXXX/handoff_for_helpers.md` を双方向で運用する。
- **運用ルール**:
  - Day0（プランニング後）: SM・Dev が当該スプリントのゴール／PBI／タスク／前提知識・参照リンクを記載し、Day1 朝までに共有。
  - スプリント末: Dev が「助っ人への申し送り欄（レビュー要点還流欄）」を **トピック別構造化（仕様変更 / DoD 強化 / 技術的負債 / プロセス改善 等）＋当該 PBI/タスク紐付け** の必須フォーマットで追記する。
  - 助っ人側: 不明点起票枠に Day1 朝までに疑問を起票（SM が当日中に回答）。
  - **役割切替すり合わせ枠（Day3 終わり 5 分）**: 助っ人間の役割切替が翌日朝に顕在化することを未然防止するため、SM が Day3 終わりに 5 分のすり合わせ枠をデフォルトでセットする。明示的な切替が発生しない週でも「枠があるから安心して報告できる」相互作用効果が得られる軽量運用。
- **由来**: Sprint001 A-2（メモ運用化）→ Sprint002 で効果確認 → Sprint003 A-8（双方向化）で完成 → Sprint005 A-16（構造化還流欄）で Day1 立ち上がり時間半減を実証し卒業反映 → Sprint008 A-39（役割切替すり合わせ 5 分枠の SM デフォルトセット）で運用ルール追補・卒業反映。

## 8. PR チェックリスト運用（案件追加・スキーマ拡張）

- **概要**: 案件追加（cases.json 行追加）およびスキーマ拡張（cases.json 構造変更）を伴う PR には `project/docs/pr_checklist.md` を必須ゲートとして適用する。
- **運用ルール**:
  - 最低限の判定軸: (a) A/B/C 比率 30% 維持、(b) スキーマ整合性確認（loader.ts 検証ロジックを通過）、(c) DoD §10（入力検証・データ保護）該当項目の確認。
  - 変更内容に応じてレビュー時点で項目追加可能。改訂はレトロまたはリファインメントで合意。
  - レビュア（PR 担当外の Dev または PO）はチェックリスト全項目に明示判定し、未充足項目があればマージブロック。
- **由来**: Sprint004 A-11（文書化のみ）→ Sprint005 A-15（cases.json 拡張 PR で初運用）で効果実証し卒業。

## 2. 依存更新の負債バックログ化と定期解消

- **概要**: 依存パッケージの更新（マイナー/メジャー）は技術負債として PBI 化し、計画的に解消する。
- **運用ルール**:
  - 検出: `pnpm audit` および定期的な outdated 確認で更新候補を起票。
  - PBI 化: 影響度（脆弱性 High/Critical → 最優先 / マイナー → 通常 / メジャー → 互換性確認込みで通常）で見積もり。
  - メジャー更新: プランニング時または着手前日までに PO 合意を取得（事後共有は緊急時のみ）。
  - 完了条件: 既存テスト全 PASS／`pnpm build` 成功／`pnpm audit` 該当脆弱性解消。
- **由来**: Sprint001 A-1（負債バックログ化）→ Sprint002 PBI-015 で初解消実績 → Sprint003 A-7（メジャー事前合意）で運用完成。

## 3. 障害物ログ運用

- **概要**: スプリント中の障害物は `scrum/impediment_log.csv` に記録し、解決後は `impediment_log_resolved.csv` に移送する。
- **運用ルール**:
  - 起票者は Dev・SM・PO の誰でも可。デイリースクラムで言及されたものは SM が当日中に起票。
  - status は `open` / `in_progress` / `resolved` のいずれか。`resolved` 確定後にレトロでまとめて移送。
  - スプリント末に新規ゼロでも `daily_scrum.md` に「新規障害物ゼロ」を明記し、運用継続を可視化。
  - **起票判定 3 軸**: デイリーで挙がった懸念は次の 3 軸すべてに該当する場合のみ `impediment_log.csv` に起票する：①スプリントゴール阻害（影響範囲）、②外部支援・交渉が必要（解消主体）、③本日中に解消不可（所要時間）。3 軸すべて No なら情報共有・自己解決事案として起票しない（軽微・即解消可と区別）。
- **由来**: Sprint001 A-4 で運用開始 → Sprint002/003 で 3 スプリント連続定着確認 → Sprint008 A-44（起票判定 3 軸）で軽微/真の障害物の判別ルールを追補・卒業反映。
- **由来**: Sprint001 A-4 で運用開始 → Sprint002/003 で 3 スプリント連続定着確認。

## 4. 追加 PBI 差し込み判断基準

- **概要**: スプリント途中で当初未計画の PBI を差し込む判断は、以下 3 条件を**全て**満たす場合のみ PO 判断で可能とする。
- **3 条件**:
  1. Day3 終了時点で計画 PBI が**全て** Done。
  2. 残バッファが**2 日以上**（1 週間スプリントの場合 Day4-5 が空く状態）。
  3. スプリントゴールの**変更を伴わない**範囲であること（ゴール変更を伴う差し込みは禁止）。
- **運用ルール**: 3 条件を満たした上で「やらない」判断（次スプリント送り）も正当。差し込み採否の理由を `daily_scrum.md` に記録。
- **由来**: Sprint002 P-2（暗黙の差し込み判断）→ Sprint003 A-6 で明文化 → PBI-019 見送り判断で実運用検証完了。

## 6. 計画ポイントの設定指針

- **概要**: スプリント計画ポイントは直近平均ベロシティを**上限の参考**とし、下限寄りで計画する。
- **運用ルール**:
  - レトロアクション・リファインメント・DoD 検証の余白を確保するため、平均ベロシティの 7〜11 割を目安に計画。
  - 新 DoD 適用直後・新領域着手スプリントは更に保守的に（下限寄り）設定。
  - ストレッチ枠は原則設けない。差し込みは項目 4 の 3 条件で判定。
  - **目安下限を割って計画する場合**は、判断根拠（新領域不確実性／新雛形/新 DoD 試行／リファインメント余白の重なり 等）を**プランニング記録に明示**する。Sprint004 で 6pt（A-13 下限 8pt から ▲2pt）計画が妥当に着地した実績をエビデンスとする。
  - Sprint005（6pt）/ Sprint006（7pt）/ Sprint007（7pt）/ Sprint008（7pt）/ Sprint009（8pt）/ Sprint010（8pt）/ Sprint011（8pt・ストレッチ +1pt）/ Sprint012（8pt・ストレッチ +1pt）と **8 スプリント連続で 6〜9pt 範囲内の計画＝実績 or 計画＋ストレッチ着地**を達成し、運用パターンとして安定（A-32 / A-45 / A-58 / A-63 / A-68 / A-70 卒業反映）。
- **由来**: Sprint002 P-2 → Sprint003 A-9（7pt 下限計画）で初適用 → Sprint004 A-13 評価で「下限割れ時の根拠明示」を補強し運用完成 → Sprint007 A-32 で 3 スプリント連続適用実績を確認 → Sprint008 A-45 で 4 スプリント連続適用実績へ更新 → Sprint009 A-58 で 5 スプリント連続適用実績へ更新 → Sprint010 A-63 で 6 スプリント連続適用実績へ更新 → Sprint011 A-68 で 7 スプリント連続適用実績へ更新 → Sprint012 A-70 で 8 スプリント連続適用実績へ更新。

## 9. 顧客フィードバックの起票・優先度判定運用

- **概要**: スプリントレビューで顧客（佐藤）から得たフィードバックは、**次スプリントのプランニング前リファインメント**で必ず起票・優先度判定の判断を行う（保留しない）。
- **運用ルール**:
  - 各フィードバック項目について、(a) 既存 PBI への統合検討、(b) 新規 PBI 起票（優先度・サイズ仮置き）、(c) 起票見送り（理由を記録）の 3 択で必ず判断する。
  - 判断期日は **次スプリントのプランニング前リファインメント完了時点**。レトロでの保留は不可。
  - 起票時は新規 PBI ID を採番し、`product_backlog.csv` に登録。優先度は High / Medium / Low の 3 段階で仮置き（プランニング時の確定可）。
  - 顧客フィードバックは『改善要望』であって『要件確定』ではないため、PO がプロダクトゴールへの寄与度で優先度判断する。
- **由来**: Sprint006 P-5（佐藤フィードバック④⑤の起票判断保留）→ Sprint007 A-29 で起票期日運用を初適用し、PBI-031 統合検討＋ PBI-036b / PBI-040 / PBI-041 新規起票完了で効果実証 → 卒業反映。

- **概要**: 1 名の開発者がスプリント内で巻取り得るタスク量の上限ガイドを設定し、属人集中を未然防止する。
- **運用ルール**:

  - **超過時の対応**: 上限超過の巻取が必要な場合は、超過理由・代替案（PR 分割／助っ人追加投入）を `daily_scrum.md` に記録した上で実施。

## 11. 沈黙の障害物確認運用

- **概要**: デイリースクラムで自発的に挙がりにくい潜在課題を意図的に表出化させる「沈黙チェック」を運用する。
- **運用ルール**:
  - **タイミング**: スプリント中盤（Day2 / Day4 を目安）に SM が意図的に問いかけを実施。
  - **問いかけ例**: 「困ってないけど時間がかかっている作業はある？」「PR が滞留しそうな兆しは？」「次タスクへの着手予定は明確か？」
  - **記録**: `daily_scrum.md` に「沈黙チェック実施」を明記し、抽出された潜在課題は Day 中の対応／翌日の予定化／障害物起票（項目 3 の 3 軸判定）のいずれかで処理。
  - **障害物ゼロ継続時の検出感度維持**: 障害物発生ゼロが連続するスプリントでは特に有効。沈黙チェックで抽出した潜在課題は障害物起票閾値に達さなくても Day 中処理を可視化することで、検出感度の客観的確認が可能。
- **由来**: Sprint006 P-6（6 連続障害物ゼロの油断警戒）→ Sprint007 A-30 で初運用（Day2 / Day4 計 2 回・潜在課題 5 件抽出）→ Sprint008 A-36 で 2 スプリント目運用（中村 TASK-001 着手宣言の早期言語化を抽出）→ 卒業反映。

## 12. CI/CD 自動化規律

- **概要**: GitHub Actions による継続的検証・本番デプロイを必須ゲートとして運用し、品質と供給網の機械的担保を行う。
- **運用ルール**:
  - **verify ジョブ**: PR / push 双方で `pnpm install → lint → tsc --noEmit → vitest run → audit → build` を必須実行。いずれか失敗でマージ／デプロイ不可。
  - **deploy ジョブ**: `main` への push 時のみ verify 通過後に GitHub Pages へ自動デプロイ。`permissions:` は最小化し、デプロイは **OIDC による短命トークン**で実施（長期トークン非使用）。
  - **Secrets 運用**: 機密値（AdSense 実 ID 等）は GitHub Actions Secrets で管理。`.env.example` には変数仕様のみ記載し、実値はリポジトリ非追跡（DoD §5-2）。
  - **`pnpm audit` ゲート**: High/Critical 検出時はビルド失敗としデプロイブロック（DoD §5-1）。
  - **サブパス公開対応**: 本番ビルド時のみ `VITE_BASE_URL` でサブパス化、`scripts/copy-404.mjs` で SPA 404 フォールバックを生成。
- **由来**: Sprint011 PBI-049（GitHub Pages デプロイ＋ CI/CD）で初確立。A-59（手動 `pnpm build` 予行観点）を超過充足する形で自動化が結実 → A-69 卒業反映。

## 13. 測定前提条件欄の運用（SEO/Lighthouse 計測の前提明示）

- **概要**: Search Console KPI / Lighthouse SEO スコア等の本番計測値を `seo_operations.md` §9 等の計測ログに追記する際、必ず「測定前提条件欄」で計測モード（本番／dist 代理）・公開後日数・既知ブロッカー（本番未到達等）を明示する。

  - 障害物（例: GitHub Pages 404）発生時も計測サイクルは中断せず、dist 代理計測で「公開時点代理値」を継続記録する。
- **由来**: Sprint021 A-95（標準フォーマット化）→ Sprint022 A-98 で運用継続 → Sprint023 で `IMP-002`（GitHub Pages 404）発生時に代理計測ルートへ即時切替できた点で運用妥当性を実証 → 2 スプリント連続定着で Sprint024 卒業反映（A-103）。

## 17. 段階展開戦略（大規模/横断的 PBI のチェックポイント分割）

- **概要**: プリレンダ/SSG/データ焼き込み等、複数データ群（章/ケース/パターン等）を横断的に変更する大規模 PBI は、データ群単位に**段階分割**し、段階毎に「機械計測＋ vitest 下限 PASS ＋ build 時間ベースライン +10% 以内」のチェックポイントを通してから次段階に進む。
- **運用ルール**:
  - **段階分割の単位**: 影響範囲がデータ群（例: reference 12 章 / cases 20 件 / patterns 20 件）など独立適用可能な軸で分割し、1 段階あたりの変更影響を限定する。
  - **各段階のチェックポイント 3 軸**: ①対象データの代表 3 件以上で view-source 等の機械計測 PASS、②既存 vitest（下限値・構造的検証）全件 PASS、③`pnpm build` 時間がベースライン +10% 以内。
  - **段階間のロールバック容易性**: 段階 N で退行検出時は段階 N のみロールバックで済むよう、段階毎に独立コミット/PR を推奨。
  - **対象 PBI 例**: プリレンダ範囲拡張・データスキーマ拡張・複数ページ同時 SEO 強化など、横断適用で退行リスクが累積するもの。
- **由来**: Sprint025 PBI-087（4 段階: hash → home → reference 12 章 → cases/patterns）で初適用 → Sprint026 PBI-098（3 段階: reference 12 章 → cases 20 件 → patterns 20 件）で 2 連続適用成功、いずれも各段階で機械計測＋ vitest 下限 PASS を維持し退行ゼロで完遂 → Sprint026 retro A-118 で卒業確定 → Sprint027 Day0 で本ファイルへ卒業反映。
